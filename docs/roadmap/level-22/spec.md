# Level 22 — A fix you can apply, and never one we applied

## Problem statement

[Level 13](../level-13/spec.md) named this in its own non-goals:

> **Retrieval-augmented *generation* of fixes.** The agent reviews. It does not
> write the patch.

That was right at the time and it left a gap the sources are explicit about: an
agentic system is expected to *act*, and every level so far ends with a
paragraph telling a human what to type. A reviewer that knows a `hashlib.md5`
call should be `sha256`, knows the line, knows the file, and then writes
"consider using SHA-256" is doing arithmetic and reporting it as advice.

The reason it was left is still valid, and it decides the whole shape of this
level. A patch generated by a language model that is then *applied* is a change
nobody reviewed, in a system whose entire argument is that a model may not
decide anything. So:

- **The system may propose. It may never apply.** Nothing here writes to the
  checkout, commits, pushes or calls a write API.
- **A suggestion is offered to a human in the platform's own format**, so
  applying it is one deliberate click by somebody with commit rights.
- **A suggestion whose patch does not apply cleanly is not published.** A
  broken suggestion is worse than none: it costs the reader the time to find
  out, and it teaches them to ignore the next one.

Capabilities addressed: **C-22** (new) — the reviewer proposes a change a human
can apply, and provably cannot apply it itself.

## Goals

1. A finding may carry a **suggested edit**: a replacement for a bounded range
   of lines in the file the finding is about.
2. Every suggestion is **validated against the file as reviewed** before it is
   published — applied in memory, and refused if the result is not what the
   recipe claimed.
3. Suggestions come from **deterministic recipes** over a finding and the source
   it names. A model may not author one.
4. The comment renders them in **GitLab's suggestion format**, so a reviewer can
   apply one from the merge request.
5. What was suggested is in the decision record, as identifiers.

## Non-goals

- **Applying anything.** No file is written, no commit is made, no API that
  changes a repository is called. A test asserts the package contains no write
  path from this level.
- **Model-authored patches.** The producer of a suggestion must be
  deterministic, for the reason [ADR 0022](../../adr/0022-a-verdict-that-can-be-audited.md)
  gives for a blocking verdict: a change a human applies in one click is a
  change they will trust as much as the gate, and an unreviewable generator
  should not be behind either.
- **Fixing everything.** Three recipes ship. A rule with no recipe produces the
  advice it always did, and a recipe that does not fit its input **returns
  nothing rather than guessing** — the whole level turns on that refusal.
- **Multi-file or multi-hunk changes.** One finding, one file, one contiguous
  range. A refactor that spans files is a merge request, not a suggestion.
- **Semantic equivalence proofs.** `md5` → `sha256` changes behaviour on
  purpose. What is checked is that the edit is the one the recipe described and
  that the file still parses, not that the program means the same thing.
- **A patch format of our own.** The suggestion carries replacement *lines* for
  a *line range*. Unified diff is a transport for something this level does not
  need, and parsing one back would be a second thing to get wrong.

## Behavioural contracts

### C-1 — A suggestion names what it answers and what produced it
Finding, file, line range, replacement lines, recipe name. The recipe is part of
it: "who decided this edit was right" is the same question Level 20 asked about
verdicts, and it has the same answer shape.

### C-2 — A suggestion is validated by applying it
The service applies the replacement to the file as reviewed, in memory. If the
range is outside the file, if the replaced text is not what the recipe matched,
or if the result no longer parses as Python, the suggestion is **discarded and
the finding keeps its prose advice**.

### C-3 — Only a deterministic producer may suggest
A finding whose producer is an `AGENT` (Level 20's attribution) never yields a
suggestion, however plausible its prose.

### C-4 — A recipe that does not fit returns nothing
No partial edits, no best guesses, no "probably". The hardcoded-secret recipe
declines when the file does not already import `os`, because a suggestion that
leaves the file failing to import is a suggestion that wastes somebody's
afternoon.

### C-5 — Bounded
A suggestion replaces at most `MAX_SUGGESTION_LINES` lines. Past that it is a
refactor, and a refactor arriving as a one-click button is how a reviewer stops
reading.

### C-6 — Rendered where it can be applied
GitLab renders a fenced ` ```suggestion:-a+b ` block as an applicable change.
The renderer emits exactly that, anchored on the finding's line.

### C-7 — Nothing is written
No filesystem write, no `git` invocation, no forge API beyond the comment this
project has always posted.

### C-8 — Recorded
The decision record gains the suggestions offered: rule, location, recipe.
Identifiers, never the replacement text — fifth level with that rule.

### C-9 — The verdict is untouched
A finding with a suggestion blocks exactly as it did without one.

## Decisions taken

**D-1 — Propose, never apply.** The one-line summary of the level. Everything
else follows from it: no write path, a human-applicable format, validation
before publishing, and a producer restriction that keeps a model out of the
authorship of anything one click from `main`.

**D-2 — Recipes, not generation.** Three deterministic transformations, each
with a pattern it must match and a refusal when it does not. A generated patch
would need a reviewer to check it, and the reviewer is the person this is
supposed to help.

**D-3 — Validated by application, in memory.** A suggestion is a claim about
what a file would look like. The cheap way to check a claim like that is to make
it true and look, which is what the service does — including re-parsing the
result, because a suggestion that breaks a build is worse than advice.

**D-4 — Replacement lines, not a diff.** The platform wants lines. The recipes
produce lines. A unified diff in between would be a format to generate and then
parse back, and both directions are places to be wrong.

**D-5 — The record carries the recipe, not the patch.** "What was suggested
here, and by which rule" is an identifier question. The replacement text is
derived from the file under review, and four levels have kept that out of the
artefacts.
